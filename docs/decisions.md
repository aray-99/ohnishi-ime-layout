# 設計判断記録

## ADR-001 日本語入力だけを最適化する

**決定:** 大西配列を常時適用せず、日本語ローマ字入力時だけ適用する。

**理由:** 英数入力と一般的なショートカットはQWERTYを維持する方が利用時の
認知負荷が低い。

## ADR-002 IMEの開閉だけで判定しない

**決定:** 日本語IMEが開いているだけではなく、かな・カナ系の日本語変換モードを
判定する。

**理由:** 利用者は日本語IME内で日本語入力と英数入力を切り替える。

## ADR-003 ショートカットはQWERTY優先

**決定:** Ctrl、Alt、Winを伴う場合は大西配列の文字変換を無効化する。

**理由:** IME状態によってショートカット位置が変わるのを防ぐ。`Ctrl + +`、
`Ctrl + -`を含む未知のアプリケーションショートカットにも一般化できる。

## ADR-004 文字キーの時間判定を行わない

**決定:** 文字キーのコード、tap/hold、時間窓、キーアップ待ちを導入しない。

**理由:** 高速タイピング時の誤判定と入力遅延を防ぐ。

## ADR-005 JIS Coreを先に完成させる

**決定:** Release 1は内蔵JISキーボードを主対象とし、US互換性はRelease 2とする。

**理由:** US物理キーボードとJIS論理配列の記号差、特にバックスラッシュが複雑で、
Coreの完成を妨げるため。

## ADR-006 US対応を独立レイヤーにする

**決定:** US物理キーボード対応は、大西配列Coreの記号定義ではなく、独立した
US互換レイヤーとして設計する。

**理由:** 目的は大西配列だけでなく、日本語IMEを維持したままLaTeX等の記号を
USのキートップに近い位置から入力することだから。

## ADR-007 CapsLock交換をCoreから分離する

**決定:** CapsLockと半角/全角の交換は当面PowerToysに残し、公開Coreに含めない。

**理由:** 大西配列の本質的要件ではなく、利用者固有設定であり、二重リマップの
原因になり得る。

## ADR-008 軽量なIssue駆動開発

**決定:** 要件・設計はInitial Commitで管理し、実装はGitHub Issue単位で行う。
Issueを満たす最終コミットまたはPRに`Closes #N`を付ける。

**理由:** 小規模プロダクトに過剰なプロセスを持ち込まず、変更理由と完成条件を
追跡可能にする。

## ADR-009 IME状態判定方式（Issue #1 技術検証）

**決定:** 対象ウィンドウの既定IMEウィンドウへ `WM_IME_CONTROL`（0x0283）を
`SendMessageTimeout`（50ms, SMTO_ABORTIFHUNG）で送り、`IMC_GETOPENSTATUS` と
`IMC_GETCONVERSIONMODE` を取得する。適用条件は
`open==1 AND (conversionMode & CMODE_NATIVE)`。取得失敗・タイムアウトはQWERTY。
カタカナ（全角/半角）はNATIVEが立つため大西配列を適用する。

**理由:** クロスプロセスで安定して取得できる方式。`ImmGetConversionStatus` は
入力スレッドのIMEコンテキストを要し他プロセスで不安定。キーボードレイアウト
（GetKeyboardLayout/言語ID）はかな/英数のサブモードを反映しない。あ/A表示など
UI観測は脆い。NATIVEビットのみで判定すれば、モードごとの細かなフラグ差や
IME実装差に影響されにくい。タイムアウト付き送信で、前面アプリのハングが
入力を止めない。

**却下:** `ImmGetConversionStatus`（プロセス跨ぎで不安定）、言語ID/レイアウト判定
（サブモード非対応）、IME表示のUI読み取り（脆い）。

**制約:** ローマ字ではないかな入力（ROMANなし）でもNATIVEが立つため本判定では
有効になる。かな入力配列は要件 §6 で対象外、所有者はローマ字使用のため実害なし。
実機の各モード値は `docs/spike-ime.md` で観測・記録する（本ADRの期待値は未検証）。

## ADR-010 キー送出方式（Issue #1 技術検証）

**決定:** 大西配列の各キーを、コンテキスト付きホットキー
`*src::Send "{Blind}dst"`（v2既定のSendInput）で実装する。SendLevelは既定（0）の
まま。`{Blind}` でShift状態を保持する。キーリピートはOSの物理キー再送による
ホットキー再発火に任せる。

**理由:** SendLevel 0 のため生成キーは自身のホットキーを再発火させず、生成キーの
再変換が起きない（要件 §7）。`{Blind}` によりShift併用時に大文字/対応記号が
自然に出力される。タイマー・Sleep・キーアップ待ち・時間窓を一切使わないため、
高速入力での欠落や遅延を避けられる（要件 §10）。

**却下・保留:** AHKのリマップ構文 `src::dst`（記号ターゲットやJISスキャンコードの
制御が明示的でなく、`{Blind}` と併せた挙動が読みにくいが機能的には代替可能）。
SendLevelを上げる方式（自ホットキーの再発火を招くため不可）。

## ADR-011 JIS/USを跨ぐキー指定（Issue #1 技術検証）

**決定:** 送出元キーは、英字（A–Z）は文字で、記号は**スキャンコード**で指定する
（`;`=SC027, `,`=SC033, `.`=SC034, `/`=SC035）。送出先の記号は**リテラル文字**で
送出する（`,` `.` `-` `;`）。

**理由:** 英字はJIS/USでVK・SCが共通。記号キーは物理位置が同じでもVKがレイアウトで
異なる（例: `;` は US で VK_OEM_1、JIS で VK_OEM_PLUS）。ソースをスキャンコードで
捉えれば物理位置を正しく拾え、ターゲットを文字で送ればAHKが現在の配列に合う
キーへ解決する。CLAUDE.md §9「印字記号＝同一VKと仮定せず実機で確認」への対応。
実機でのVK/SC確認手順は `spike/ime-spike.ahk` の identify 機能で提供する。

## ADR-012 git-flowとConventional Commitsの採用（Issue #8）

**決定:** 分岐モデルにgit-flowを採用する。`main` はリリース専用（タグ付け）、
`develop` を統合ブランチとし、各Issueは`feature/issue-<n>-<short-name>` を
`develop` から切り、`--no-ff` で`develop` へマージする。リリースは
`release/<version>` を`develop` から切って`main` へマージ・タグ付けし、`develop`
へ戻す。コミット件名はConventional Commitsに従う。詳細は `CONTRIBUTING.md`。

**理由:** 所有者の明示的な指示。リリースとホットフィックスの経路を分け、`main`
を常にリリース可能な状態に保つ。CLAUDE.md §4.5 の `issue-<n>-<short-name>` は
git-flowの接頭辞を付けて `feature/issue-<n>-<short-name>` に統合し、両立させた。

**経緯:** 本方針はIssue #1（技術検証）のマージ後に採用したため、#1はsquashで
`main` に直接入っている。公開済み履歴は書き換えない（CLAUDE.md §14）ため、
`develop` は#1を含む現在の`main` をベースに作成した。以降のRelease 1作業は
すべて`develop` 経由で進め、Release 1で`develop → main` をマージ・タグ付けする。

## ADR-013 修飾キー判定は論理状態を使う（Issue #14・実機検証で判明）

**決定:** Ctrl/Alt/Winのバイパス判定を物理状態（`GetKeyState(..,"P")`）ではなく
**論理状態**（`GetKeyState(..)`）で行う。

**理由:** 所有者はPowerToysで 無変換→Ctrl をリマップしている。この注入された
Ctrlは物理状態に現れず、`"P"` 判定ではバイパスが効かないため、日本語入力中に
大西配列が Ctrl 併用でも発火し、`無変換+D → Ctrl+A → 全選択` のように壊れていた。
論理状態なら他リマッパ（PowerToys等）による修飾キーも検出できる。実キーのCtrlは
両方式で検出できるため後退はない。自スクリプトはCtrl/Alt/Winを送出しないため、
論理状態が誤って立つことはない。実機（Edge, 無変換+D）で確認予定。

**却下:** 物理状態のみ（PowerToys等のリマップ修飾キーを取りこぼす）。

## ADR-014 IME判定はフォーカスコントロールで行う（Issue #14・実機検証で判明）

**決定:** IME状態は、前面ウィンドウのトップレベルhwndではなく、
`GetGUIThreadInfo` で得た前面スレッドの **フォーカスhwnd** に対して問い合わせる
（フォーカスが取れない場合は前面ウィンドウにフォールバック）。

**理由:** Windows 11の新メモ帳（TSF/WinUI）はトップレベルhwnd経由の
`WM_IME_CONTROL` にIME状態を返さず、大西配列が起動しなかった。フォーカスhwnd
（`GetGUIThreadInfo.hwndFocus`）へ問い合わせると新メモ帳でも `open`/変換モードが
取得できることを実機で確認した。Chromium/Electron・Win32アプリ（Edge等）は
従来どおり動作する。これはCLAUDE.md §6「近代アプリ対応」の範囲での堅牢化。

**却下:** トップレベルhwndのみ（新メモ帳等のTSF/WinUIアプリでIMEを取りこぼす）。

## ADR-015 IME判定はキャッシュから読む（Issue #24・実機診断で判明）

**決定:** リマップ判定 `Layout.ShouldApply()` は、毎打鍵でIMEへ問い合わせるのを
やめ、**背景タイマー（25ms間隔）で更新するキャッシュ `Ime.Composing`** を読む。
問い合わせ本体 `Ime.IsJapaneseComposition()`（WM_IME_CONTROLのクロスプロセス送信）は
タイマー内でのみ実行する。

**理由:** 毎打鍵でクロスプロセスの `SendMessageTimeout` を行うと、その間キーボード
フックがブロックされ、高速入力時にキーの取りこぼし・順序乱れが発生していた
（例: 「メモ帳」→「あめfもty」。実機診断では全打鍵 applied=1・修飾なしでも化けた＝
判定は正しいが実行時にフックが拾えていない）。キャッシュ読み取りはフックを
ブロックしないため、取りこぼし・順序乱れが解消する。ADR-009の「毎入力問い合わせ」を
本ADRで置き換える。

**トレードオフ:** キャッシュは最大1間隔（25ms）古い可能性がある。影響はIMEモード
切替の直後〜25msに限られ、人がモード切替後に打鍵するまでの間隔より十分短い。
バースト中はモードが変わらないためタイマーが遅延しても正しい値のまま。

**却下:** 毎打鍵での同期問い合わせ（フックをブロックし#24を起こす）。
